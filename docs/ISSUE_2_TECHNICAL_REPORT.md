## 問題如何被誤判

最初的分析從 `sprite id 0` 反推遊戲腳本變數 221／222／223，並把沒有預設分支
解讀為原始資料漏洞。這段靜態分析能解釋「0 如何成為非法 zone」，卻沒有在玩家
現場量到變數真的因該分支而成為 0。後來取得玩家存檔，並用相同核心資料重跑後，
才有能力直接檢查玩家實際路徑。

GOG 與既有資料的核心檔案逐位元相同，排除了「玩家買到另一個 Elvira 發行版本」
這條假說。真正可重現的差異來自中文化疊層：畫面顯示的位置與滑鼠命中換算不是
同一個矩形。玩家看到並點擊某個方向或動詞時，引擎可能收到旁邊的 hitarea，接著
走入錯誤腳本分支；`sprite id 0` 是錯誤輸入的下游表徵，而不是版本差異本身。

## 修正內容

v1.2.3 對應的修正集中在三點：

1. 滑鼠輸入改用 overlay active area，並依執行時 overlay 寬高還原至遊戲的
   320×200 座標，不再混用 `gameDrawRect`。
2. 戰鬥紅底命令顯示時停止繪製一般中文動詞，避免遮住
   `LUNGE`／`HACK`／`BLOCK`／`PARRY`。
3. 撤銷 v1.2.1 會吞掉缺圖錯誤的路徑；保留獨立、在陣列取值前執行的 zone
   上界防護。上界防護的分析另見 [`BUG_ZONE_BOUNDS.md`](BUG_ZONE_BOUNDS.md)。

### v1.2.3 後的存讀檔 Enter 修正

先前為符合原版手冊，補丁在 AGOS 的全域鍵位表把 `RETURN` 與 `KP_ENTER` 綁到
「跳過片頭」自訂動作。註解聲稱只在 cutscene 期間生效，但鍵位表實際在整場遊戲
啟用。因此檔名輸入迴圈雖可收到一般字母，Enter 卻在鍵位映射層被轉成自訂動作，
`userGame()` 永遠等不到 `_keyPressed`，表現就是玩家所述的「輸入名稱後按 Enter
沒有反應」。

修正移除這兩個全域映射；Escape 與手把 `JOY_Y` 仍可跳過片頭。同時讓 Elvira 1
的檔名輸入迴圈和 AGOS 其他存檔介面一致：Return、數字鍵盤 Enter 與 Backspace
以 `keycode` 判斷，可列印檔名字元才使用 `ascii`。這也涵蓋 macOS／輸入法可能送出
「keycode 正確、ascii 為 0」的控制鍵事件。

## 驗證邊界

開發端已用玩家存檔、GOG 原始資料、OpenGL 與 4:3 非整數縮放重跑原操作；該輪
可以直接點中文字中心，程序持續存活，log 未見 zone 0 或 `sprite id 0`。這證明
修正涵蓋了已建立的控制重現路徑，但不能替代玩家的 macOS 實機驗收。

issue 的最新證據指出兩條尚未關閉的玩家路徑：

- 存讀檔畫面輸入檔名後按 Enter 的問題，已在開發端完成根因修正與真實 GUI
  回歸，仍待玩家 macOS 驗收。
- 遇到戰鬥時仍出現先前錯誤；目前公開留言未提供足以判定是否仍為同一個
  `sprite id 0` 路徑的新 log 或錯誤字串。開發端由玩家 slot 1 走到後續 NPC
  對話，多輪程序存活且未見 `001.VGA`／`002.VGA`／`sprite id 0`，但尚未完成
  與玩家影片相同的守衛戰，不能當作該路徑通過。

因此目前可以說「座標錯位根因已被證實且部分玩家驗收通過」，不能說「所有當機、
凍結與存讀檔問題均已解決」。

## issue 關閉條件

1. 以玩家原存檔在 macOS 重跑守衛戰，確認守衛出現、戰鬥命令可點、無
   `001.VGA`／`002.VGA`／`sprite id 0`，且戰鬥可繼續。
2. 在存檔與讀檔各完成一次文字輸入、Enter 確認、離開選單與重新載入；保留
   log 及存檔雜湊。
3. 全螢幕與視窗互切後重做上述兩條，確認 overlay active area 重建後仍一致。
4. Linux、Windows、macOS 的實際出貨包各做同路徑冒煙測試；不能只測工作樹執行檔。
5. 玩家確認原回報路徑通過後，再關閉 issue #2。
