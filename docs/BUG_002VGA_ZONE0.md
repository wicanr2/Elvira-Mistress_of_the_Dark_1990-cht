# 撞牆就中止:`Can't load 002.VGA` 的追查與修正

> **2026-08-02 勘誤（issue #2 的玩家存檔與 GOG 版實測）**：本文件原先把
> `sprite id 0` 歸因為遊戲資料漏洞，證據只到靜態腳本推論，沒有量到現場變數；
> 玩家後續證明 v1.2.1 的「缺圖就略過」會把中止改成永久凍結。取得玩家存檔後，
> 又確認 GOG 與原開發資料的 `GAMEPC`、`TBLLIST`、`TABLES*`、VGA 等核心檔案
> 位元完全相同，版本差異不成立。實際根因是繁中 overlay 以
> `overlayDrawRect` 顯示，但 `showOverlay(false)` 讓滑鼠依 `gameDrawRect` 換算；
> 4:3、Retina 或視窗縮放下兩矩形不同，玩家看到的方向／動詞位置與命中位置
> 分離，腳本因錯誤輸入走到圖號 0。修正為 overlay active area 輸入並按實際
> overlay 尺寸還原至 320×200 後，同一份存檔、同一路徑不再要求 zone 0。
> 以下保留原追查全文，作為錯誤結論如何形成的可追溯紀錄；其中「遊戲資料本身
> 的漏洞」與「跳過缺圖即安全」均已被新證據推翻，不可再當作現行結論。

《古堡禁地》的玩家往前走撞到欄杆或牆壁時,遊戲會整個中止,終端機留下一行:

```
ERROR: loadVGAVideoFile: Can't load 002.VGA!
```

原追查當時的結論（現已由上方勘誤推翻）是:**這是遊戲資料本身的漏洞,不是中文化造成的,也不是玩家的檔案缺損。** 遊戲腳本裡有一段條件分派沒有預設分支,八個條件都不符合時會讓畫面編號停在 0;編號 0 換算出來的圖檔在 DOS 磁片版根本不存在,而 ScummVM 遇到找不到的圖檔就直接中止整個遊戲。

三十五年前的遊戲資料改不了,能改的是不要讓它殺掉遊戲。現在遇到載不到的圖就跳過並印一行警告,最壞情況是某個畫面元素沒畫出來,玩家不會被踢出去、也不會賠掉進度。

回報者是 [@wesley316-Guybrush](https://github.com/wesley316-Guybrush)([issue #2](https://github.com/wicanr2/Elvira-Mistress_of_the_Dark_1990-cht/issues/2))。他提供了兩份完整的終端機 log(分別在兩種不同的顯示後端下)、四段錄影,以及最關鍵的一句話——**「只要是往前走遇到欄杆或牆壁都會出現」**。最後查到的三個變數,存的正是同一場景三個方向的畫面編號——那句描述直接指向了根因。

## 症狀與現場資料

| 項目 | 內容 |
|---|---|
| 觸發 | 往前走撞到欄杆或牆壁;玩家描述為「進去後往兩邊走碰壁後就出現」 |
| 表現 | 遊戲中止,終端機印 `ERROR: loadVGAVideoFile: Can't load 002.VGA!` |
| 版本 | `agos:elvira1` — Elvira: Mistress of the Dark (Floppy/DOS/English) |
| 顯示後端 | SurfaceSDL 與 OpenGL 兩種都會發生 |
| 中文化版本 | v1.1 與 v1.2 都會發生 |

玩家的 log 裡,錯誤前一行是 `AGOSEngine::stopMusic()`,再往前是正常的中文化載入訊息。

## 前提

追查建立在幾個前提上,先寫在明處:

1. 玩家與開發端使用的是**同一個發行版本**。依據是兩邊的 ScummVM 偵測結果都是 `Elvira: Mistress of the Dark (Floppy/DOS/English)`。
2. 玩家的遊戲檔**沒有缺損到影響偵測**。ScummVM 的偵測會比對指紋,若主要檔案缺失或被改過,啟動時就會失敗或報不同的版本。
3. 反組譯出來的腳本,反映的是**遊戲原檔的內容**,不受中文化影響。中文化只在 `getStringPtrByID` 出口換字串,不改遊戲原檔、也不改腳本位元組。
4. 開發端手上的遊戲檔與玩家的檔案清單**尚未逐檔比對過**(見〈開放項目〉)。

## 先排除中文化自己

在往遊戲資料查之前,得先確認不是自己造成的。四項檢查:

| 檢查 | 結果 | 驗證方法 |
|---|---|---|
| patch 有沒有碰 zone 載入 | 沒有。全文比對,中文化 patch 未修改任何 zone 載入相關程式碼 | Inspection |
| patch 有沒有寫遊戲腳本變數 | 只有一處:F7 無敵模式寫 `_variableArray[5]`(生命值) | Inspection |
| 玩家有沒有用過 F7 | 沒有。F7 會印 `CHT: godmode`,玩家的兩份 log 都沒有這行 | Test |
| 是不是顯示層造成的 | 不是。SurfaceSDL 與 OpenGL 兩條完全不同的路徑都會發生 | Test |

`_variableArray[5]` 確認是生命值,不是別的用途——引擎的 `printStats()` 把它印在狀態列的 `LIF` 欄位(Inspection)。這條特別要確認,因為 F7 寫入的值是 99,而 99 除以 100 剛好是 0,與症狀的數字巧合。玩家沒按過 F7,這條排除。

## 根因

### 編號 0 從哪來

ScummVM 的 AGOS 引擎用 `setImage(圖號)` 畫一張圖,而它算「這張圖在哪個 zone 檔」的方式很直接:

```cpp
zoneNum = vgaSpriteId / 100;
```

zone 檔的檔名規則是「兩位數 zone + 一位數類型 + `.VGA`」,所以 zone 0 的檔案叫 `001.VGA` 與 `002.VGA`。

而 Elvira 1 的 DOS 磁片版**沒有 zone 0**。實際盤點遊戲夾裡的 130 個 `.vga` 檔,zone 編號是 01、02、03、06–09、17–74(Test)。也就是說,只要圖號小於 100,算出來就是一個不存在的 zone。

### 小於 100 的圖號從哪來

這一段要靠反組譯。ScummVM 內建兩套 dump 工具,分別對應遊戲的兩種腳本:

- `dumpAllVgaScriptFiles()` — 各 zone 的動畫腳本
- `dumpAllSubroutines()` — GAMEPC 的遊戲邏輯子程式

先看動畫腳本:把遊戲夾裡實際存在的 64 個 zone 全部 dump,共 13,120 行。畫圖的指令 `SET_WINDOW_IMAGE` 出現 157 次,參數最小的是 201,**沒有任何一個小於 100**(Test)。

再看遊戲子程式。這裡有個容易踩空的地方:`dumpAllSubroutines()` **只會 dump 當下載入在記憶體裡的子程式**。Elvira 1 的腳本分散在 11 個 `TABLES*` 分頁,遊戲會依區域載入。第一次 dump 只拿到約 13 萬行;補上一輪 `loadTablesIntoMem()` 把所有分頁都載進來之後是 17 萬行——而下面這幾行,正是補上之後才出現的。

子程式裡的 `PICTURE` 指令,參數大多是常數(最小 100,對應 zone 1,合法)。但有七處不是常數,而是**變數**:

```
PICTURE [221] 4      ← 子程式 50
PICTURE [222] 4      ← 子程式 53
PICTURE [223] 4      ← 子程式 48、51、55
```

方括號表示「讀這個編號的變數,拿它的值當圖號」。

### 沒有預設分支

那三個變數在整份腳本裡只有一個地方會被指派,就是子程式 74:

```
SUB_74:
  CHILD_FR2_IS SUBJECT_ITEM <物件A> ->  SET 221 300   SET 222 301   SET 223 302  …
  CHILD_FR2_IS SUBJECT_ITEM <物件B> ->  SET 221 300   SET 222 301   SET 223 302  …
  CHILD_FR2_IS SUBJECT_ITEM <物件C> ->  SET 221 5000  SET 222 5001  SET 223 5002 …
  …共八組…
```

八組條件,每組檢查目前的對象是不是某個特定物件,然後設定該場景三個方向的畫面編號。

**八組都不符合時,沒有預設分支。** 221/222/223 保持原值;如果從遊戲開始到那一刻都沒有任何一組命中過,值就是 0。接著子程式 48/50/51/53/55 之一執行 `PICTURE [221]`,把 0 送進 `setImage`,zone 算成 0,找不到 `002.VGA`,`error()` 中止。

這也解釋了玩家為什麼是「往兩邊走碰壁」時遇到:那三個變數存的正是**同一個場景三個方向的畫面編號**,轉向就會讀到其中一個。

## 為什麼 ScummVM 選擇中止

`loadVGAVideoFile()` 有一個 `useError` 參數,傳 `false` 就只是回傳空指標而不中止。但呼叫端 `setImage()` 與 `animate()` 的主迴圈長這樣:

```cpp
for (;;) {
    vpe = &_vgaBufferPointers[zoneNum];
    if (vpe->vgaFile1 != nullptr) break;
    loadZone(zoneNum);
}
```

迴圈要等載入成功才跳出。**如果只是把載入改成不致命,`vgaFile1` 永遠是空的,迴圈永遠跳不出來**——把中止換成當場凍結,對玩家更糟。從這個角度看,上游選擇 `error()` 是合理的:在這個結構下,那是唯一不會凍結的做法。

## 修法

正解是在**進迴圈之前**先試載一次,真的沒有就跳過這張圖:

```cpp
zoneNum = (getGameType() == GType_PN) ? 0 : vgaSpriteId / 100;

// 缺 zone 檔時跳過該圖, 不要 error() 中止整個遊戲。
// 注意不能只把 loadZone 改成非致命: 下面的 for(;;) 靠 vgaFile1 非 null 才跳出,
// 載入失敗會變成無窮迴圈。
if (_vgaBufferPointers[zoneNum].vgaFile1 == nullptr) {
    loadZone(zoneNum, false);
    if (_vgaBufferPointers[zoneNum].vgaFile1 == nullptr) {
        warning("%s: zone %d 載不到(sprite id %d), 跳過此圖以免中止遊戲",
                __FUNCTION__, zoneNum, vgaSpriteId);
        return;
    }
}

for (;;) { … }
```

`setImage()` 與 `animate()` 各一份,兩者都有同樣的迴圈結構。

| 項目 | 結果 | 驗證方法 |

| 修正後走同一條路徑 | 印警告後繼續執行,跑滿 45 秒測試時間沒有中止 | Test(強制 `setImage(99)` 觸發 zone 0) |

| 三個變數只在子程式 74 指派 | 24 處指派,分成 8 組,值域 300–5102 | Test(全 TABLES dump) |
| 「八組都不命中時值為 0」 | 由腳本結構推導,未在現場量到那一刻 | Analysis |

最後一列是這次分析裡強度最弱的一環,見〈有效性威脅〉。

### 重現不出來這件事

用開發端的遊戲檔跑了 **150 次**與 **80 次**兩輪隨機移動(前後左右,含大量撞牆),**都沒有重現**(Test)。

這不代表機率低。隨機走訪不是對房間圖的均勻覆蓋,而觸發需要「走到某個使用變數畫面的場景」加上「該場景的對象不在那八組之內」兩個條件同時成立。要從「沒重現」推出任何機率結論,得先做系統性的房間走訪,目前沒有做。

## 上游現況

ScummVM 已改用日期版號,最新是 2026.3.0(2026-06-20);本專案的基準 v2.9.1 是 2025-05-25,中間隔了三個大版本。

把 v2.9.1 之後所有 **58 個** AGOS 引擎相關提交掃過一遍,**沒有任何一個處理這個情況**(Test)。近期 AGOS 的維護集中在 Atari ST / Amiga / Acorn 版本的音樂與顯示。結論是升級 ScummVM 版本救不了這顆,得自己擋。

查證時有個插曲值得記:ScummVM 的 GitHub issue 功能是關閉的(`has_issues: false`),所以用 `gh search issues` 查會回空。空結果是管道沒接上,不是「查無此問題」——先用一個必然存在的關鍵字做正對照,才確認了這件事。

## 結論

1. 中止的直接原因是 `setImage()` 拿到小於 100 的圖號,換算成不存在的 zone 0。
2. 圖號來自遊戲腳本變數 221/222/223,而指派這三個變數的子程式 74 是八組條件分派,沒有預設分支。
3. 這個漏洞在遊戲原始資料裡,與中文化無關,也與顯示後端無關。
4. ScummVM 在這個呼叫結構下選擇 `error()` 中止是合理的:單純把載入改成不致命會導致無窮迴圈。
5. 在進迴圈前擋下缺檔情況,可以在不改變正常路徑行為的前提下避免中止。修正後正常遊玩 80 次移動的誤觸發次數為 0。
6. 升級到目前最新的 ScummVM 不能解決這個問題。

## 建議

1. 這道防護保留在本專案的 patch 內,不追上游版本。
2. 玩家更新後回到原本會出事的位置實測,回報畫面是否有元素缺失。
3. 若要進一步定位是哪個對象未命中八組條件,需要玩家出事前的存檔;取得後在 `SUB_74` 入口加暫時性 log 印出 `SUBJECT_ITEM` 即可。
4. 其他 AGOS 遊戲的中文化專案可直接沿用這道防護,`setImage()` 與 `animate()` 的迴圈結構在各 subengine 相同。

## 有效性威脅

**內部效度(是不是真的這個原因造成)。** 根因是靜態推導出來的:反組譯看到結構漏洞,加上症狀吻合(觸發時機、三個方向的變數語意、數字對得上),但**沒有在現場量到「變數確實是 0」那一刻**。緩解方式是把驗證打在失敗路徑本身——強制走一次 zone 0,確認修正後不再中止。要完全證實推導,需要玩家的存檔。

**外部效度(能不能推廣)。** 只在 Floppy/DOS/English 版上驗過。Amiga 與 Atari ST 版的 zone 檔名規則不同(`.pkd`、`.out`),防護邏輯本身與檔名無關,應該同樣適用,但沒有實測。其他 AGOS 遊戲(Simon、Waxworks)的迴圈結構相同,同樣未實測。

**建構效度(量的東西是不是要量的東西)。** 「防護觸發 0 次」只證明正常路徑沒被誤擋,不證明所有缺圖情境下跳過都安全——跳過一張關鍵背景圖仍可能讓畫面難以辨認。判定「畫面正常」用的是人工看截圖,不是像素比對。

**結論效度(資料分析可不可信)。** 「230 次移動沒重現」不能推論觸發機率低,理由寫在前面。反組譯的完整性也有限:結論建立在「全部 TABLES 分頁都載入了」這個前提上,而唯一的依據是補上載入迴圈後 dump 行數從 13 萬增加到 17 萬。沒有做「再多載一輪還會不會變多」的收斂測試,所以不能排除仍有分頁沒進來。

## 可移植的部分

給其他做 AGOS 引擎中文化的人,有三件事可以直接拿去用。

防護本身可以照抄——`setImage()` 與 `animate()` 是各 subengine 共用的同一份程式碼,迴圈結構相同。

反組譯時記得先把分頁載滿。`dumpAllSubroutines()` 只 dump 記憶體裡現有的子程式,要先跑一輪 `loadTablesIntoMem()`;少了這步會漏掉大半腳本,而且漏掉的部分不會有任何提示,dump 出來一樣看起來很完整。

玩家描述症狀的用詞值得逐字讀。這次「往兩邊走」直接對應到「同一場景三個方向的畫面編號」,比翻遍靜態分析都快。

同一份分析也收錄在 [scummvm-agos-cjk](https://github.com/wicanr2/scummvm-agos-cjk) 的 `AGOS_PITFALLS.md` §3.7,那個 repo 收集 AGOS 引擎中文化的共用修正。
